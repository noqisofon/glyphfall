# ADR-0013: 突発イベント発生システム（トリガー／抽選エンジン）の設計

- Status: Accepted
- Date: 2026-09-15

## Background

ADR-0004 で「旅シミュレーション中に突発イベント（山賊、野生動物、仲間になるかもしれないキャラ、
行き倒れの旅人、検問・天候急変など）を挟む」という創発設計は決まっていたが、それは
「どんなイベント内容があるか」というコンテンツ側のリストに過ぎない。
「いつ判定を行うか」「複数の候補からどれが選ばれるか」「一期一会のイベントを何度も引かないよう
どう抑制するか」といった、突発イベントを実際に *発生させる仕組み* 自体は一切設計されていなかった。

さらに、突発イベントの中身（会話文・条件・効果）を将来 Lua で外部記述できるようにしたいという
動機があった。しかし発生の仕組みが未設計のまま「Luaでどう書くか」を先に決めてしまうと、
スクリプト側のAPI形状が先行して発生エンジンの設計を歪めてしまう恐れがある。

## Circumstances

発生システムに必要な要件を洗い出すと、以下が最低限決まっていないと実装に着手できないことが分かった。

1. **発生タイミング**: ADR-0004の「移動姿勢（慎重／普通／大胆）」はエンカウント*率*を決めるだけで、
   その率でロールした後に「何を出すか」を決める仕組みが存在しない。
2. **候補の絞り込み**: 山賊とクマは何度でも起きてよいが、「仲間になるかもしれないキャラとの遭遇」は
   ADR-0004で「一期一会の緊張感」と明記されており、同じ相手に何度も遭遇しては緊張感が壊れる。
   条件（一発限りか、クールダウンが必要か、パーティ状態や場所に応じて出現可否が変わるか）を
   イベントごとに持たせる必要がある。
3. **データ指向との整合**: ADR-0006でBevy ECSを採用し、「シミュレーションロジックをデータ指向で扱う」
   方針を明言している。突発イベントの一覧をコード内のif分岐で埋め込む設計は、この方針や将来のLua外部化
   のどちらとも相性が悪い。
4. **将来のLua外部化との接続**: 「発生判定（いつ・どれが選ばれるか）」と「発生後の効果（会話・戦闘突入・
   仲間加入など）」を同じ層に混在させると、後からLuaを差し込む際に発生エンジンごと作り直す羽目になる。

## Rationale

上記4点を踏まえ、発生システムを以下のように層で分離することにした。

- **ロール頻度とロール結果の分離**: 「発生するかどうか」（ADR-0004の姿勢別エンカウント率など、
  呼び出し元コンテキストが握る確率）と、「発生するとして何が選ばれるか」（本システムが握る抽選）を
  別の責務にする。こうすることで、旅シミュレーション以外の文脈（町の徘徊、宿泊時など）が将来
  追加されても、それぞれが自分の確率だけ渡して同じ抽選エンジンに乗っかれる。
- **イベント定義をデータとして持つ**: イベントごとに「タグ（対象コンテキスト：旅／町／ダンジョンなど）」
  「条件（影響度・所持フラグ・時間帯など）」「重み」「再発生ルール（無制限／クールダウン／一発限り）」を
  構造体として保持する。ADR-0006のデータ指向方針に沿い、将来的にはこの構造体をLuaテーブルから
  ロードする形へ差し替えやすくなる。
- **抽選は2段階**: (1) 呼び出し元が渡す基礎確率で「何か起きるか」を判定 → (2) 起きるなら、現在の
  コンテキストに合致し、条件とクールダウンを満たす候補群から重み付き抽選で1件選ぶ。
  ADR-0004の表（慎重／普通／大胆でエンカウント率が変わる）は(1)にそのまま対応し、
  「仲間になるかもしれないキャラ」のような希少イベントの出やすさは(2)の重みで個別に調整できる。
- **発生後の効果はエンジンの外に置く**: 抽選エンジンは「どのイベントIDが選ばれたか」という
  Bevyイベント（`SuddenEventTriggered`）を発火するところまでを責務とし、実際に会話ウィンドウを開く・
  戦闘に突入する・仲間候補フラグを立てるといった効果処理は、そのイベントを購読する側（当面はRustの
  ハンドラ）に委ねる。この境界を先に切っておけば、後日「効果処理をLuaスクリプト呼び出しに差し替える」
  というADRを、抽選エンジン自体には手を入れずに書ける。
- **一発限り／クールダウンは履歴リソースで管理**: 抽選のたびにイベント定義を書き換えるのではなく、
  「どのイベントがいつ最後に発生したか／一発限りイベントが発生済みか」を別リソース
  （`SuddenEventHistory`）に記録し、候補の絞り込み時に参照する。イベント定義自体はイミュータブルな
  マスタデータのまま保てる。

## Decision

突発イベント発生システムを、抽選エンジンと効果処理を分離した2段階抽選方式で設計する。

- 新設するモジュール（例: `src/event/`）に以下を置く。
  - `SuddenEventDef`: イベント定義（id、対象コンテキストタグ、発生条件、重み、再発生ルール
    〔`Unlimited` / `Cooldown(ticks)` / `OneShot`〕、カテゴリ）。ADR-0004記載の初期カテゴリ
    （山賊、野生動物、仲間候補、行き倒れの旅人、検問、天候急変）をひとまずこの構造体で表現する。
  - `SuddenEventRegistry`: 起動時にロードする `SuddenEventDef` の一覧を保持するResource。
  - `SuddenEventHistory`: イベントごとの最終発生時刻・OneShot消化済みフラグを保持するResource。
  - `SuddenEventTriggered`: 選ばれたイベントIDとコンテキストを載せて発火するBevy Event。
- 発生判定は2段階で行う関数（例: `try_trigger_sudden_event(context, base_probability, rng)`）として実装する。
  1. 呼び出し元（旅シミュレーションなど）が渡す `base_probability`（ADR-0004の姿勢別エンカウント率）で
     「何か起きるか」をロールする。
  2. 起きる場合、`context`（現在地・旅/町/ダンジョンの別など）に合致し、`SuddenEventHistory` 上で
     クールダウン／OneShotの制約を満たす候補を `SuddenEventRegistry` から抽出し、`weight` に基づく
     重み付き抽選で1件選ぶ。候補が0件なら何も起こさない。
  3. 選ばれたら `SuddenEventHistory` を更新し、`SuddenEventTriggered` を発火して終了する。
     実際の演出・分岐（会話・戦闘・仲間加入判定など）はこのイベントを購読する既存の各システム側で
     処理し、抽選エンジン自体はその中身に関知しない。
- 本ADRの時点ではADR-0004の旅シミュレーションへの組み込みのみをスコープとし、町中徘徊や宿泊時などへの
  発生タイミング拡張は将来の課題とする（`context` にタグを持たせる設計自体は最初から汎用化しておく）。
- イベント定義の記述言語（Rustのリテラル定義か、Luaなど外部スクリプトからのロードか）は本ADRでは決定
  しない。`SuddenEventDef` と効果ハンドラの境界を明確に切ったことで、Lua導入は別ADRとして後日
  「`SuddenEventRegistry` のロード元をLuaに差し替える」「効果処理をLua関数呼び出しに委譲する」という
  局所的な変更として扱えるようにする。
- `context` の具体的なフィールド構成（現在地・旅/町/ダンジョンの別に加え、影響度やパーティ状態を
  どこまで含めるか）は本ADRでは確定させない。むやみに肥大化させないことだけを方針とし、実際の型は
  実装コミットまたは後続ADRで決める。
- クールダウン・OneShotの制約で候補が0件になり「何も起きないティック」が続くことは許容するが、
  ADR-0004の「大胆に」で厳選速度を稼ぐプレイスタイル（仲間候補イベントを繰り返し狙う）を潰さないよう、
  希少カテゴリのクールダウン値は実装・調整時に旅の周回頻度と突き合わせて検証する。

### スコープ外（将来の別課題）

ADR-0005の「苦難の乙女」特性（幼馴染が定期的に攫われ、救出クエストが安定収入源化する創発的な
不具合気味の挙動）について、本ADRの再発生ルール（`Unlimited` / `Cooldown` / `OneShot`）で
誘拐イベント自体を表現することは可能（対象幼馴染が苦難の乙女特性を持つ間 `Unlimited` として扱えばよい）。
ただし、これは「攫う側」の勢力（山賊など）が個体・拠点単位で討伐・全滅しうる永続シミュレーションを
前提にしたときに限り、「勢力を全滅させても誘拐イベントのために攫う側を強制的に補充する」という
矛盾が表面化しうる。本ADRの時点では山賊などの勢力を個体・拠点単位で永続管理する仕組み自体が
未設計であるため、この矛盾への対処（誘拐イベントは勢力の生存確認を参照しない、抽象的な「何者か」に
攫わせる、など）は本ADRのスコープ外とし、そのような永続勢力シミュレーションを設計する将来のADRに
持ち越す。
