# ADR-0006: Bevy ECS と罫線グリッドによるターミナルUIアーキテクチャ

- Status: Accepted
- Date: 2026-09-13

## Background

本作『Glyphfall』は、「Daggerfall × ドラクエ」というコンセプトを表現するにあたり、膨大なテキスト、パラメータ、メッセージ、三分割ウィンドウを画面上に効率よくレンダリングする必要がある。
また、豪華な3Dモデルや高解像度スプライトに依存せず、等幅フォントと罫線文字（ASCII/Unicode）による「レトロCUI × ドラクエ」という独自の視覚的アイデンティティ（社名・プロジェクト名通りのGlyphfall）を低アセットコストで確立したい。

## Circumstances

ゲームエンジンおよびUI実装方式の選定において、以下の選択肢を検討した：
1. **純粋なターミナルCUI（ratatui / crossterm等）**: 本物の端末エミュレータ上で動かす。
2. **汎用ゲームエンジンのGUI機能（Unity / Godot）**: エンジン標準のCanvasやControlノードでUIを構築する。
3. **Rust + Bevy Engine (0.15) によるカスタム罫線グリッド描画**: BevyのECSノード上で、等幅フォントとUnicode罫線文字を用いて自前で枠線とテキストを組み立てる。

## Rationale

純粋なターミナルCUI（1）は動作が軽量だが、将来的なCRTスキャンライン・燐光グローのポストプロセスシェーダー、サウンド再生、細かな解像度・アスペクト比制御の面で制約が大きい。
汎用ゲームエンジン（2）はGUIが最初から揃っているが、大量のシミュレーションロジックや創発イベントをデータ指向で扱うことや、「文字セル単位のグリッド計算」をベースにする本作の設計とはやや距離がある。

Bevy Engine（3）を採用することで、以下の利点が得られる：
- Rustの型安全性とBevyのECS（Entity Component System）により、ゲームシミュレーション（NPC、イベント、ステータス）とUIコンポーネントを同一のデータ指向モデルで一元管理できる。
- ビットマップ画像を使わず、Unicodeの罫線文字（`┌─┐│└─┘`）をグリッド配置してウィンドウ枠を動的に構築するプリミティブ（`spawn_message_window`）を用意すれば、桁数（`inner_cols`）と行数（`inner_rows`）を指定するだけで任意のウィンドウ枠を高速に量産できる。これは会話の三分割レイアウトにも直結する。
- ドラクエ的な「1文字ずつメッセージ送り」演出も、`TypewriterMessage` コンポーネントと `typewriter_tick` システムとして疎結合に実装できる。

## Decision

開発基盤として Rust + Bevy Engine (0.15) を採用する。
UI描画はビットマップ画像ではなく、Unicode罫線文字を用いた等幅セルグリッド自動生成アーキテクチャを採用し、メッセージ送り演出をECSコンポーネントとして分離管理する。
将来的なCRT風ポストプロセスシェーダーや複数分割ウィンドウ配置への拡張を見据えた設計とする。
