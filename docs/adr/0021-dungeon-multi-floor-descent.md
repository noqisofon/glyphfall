# ADR-0021: 封魔の地下迷宮の複数階層化（B1F〜B6F）

- Status: Accepted
- Date: 2026-09-16

## Background

ADR-0017でCave生成に置き換えて以降、王都南東の「封魔の地下迷宮」は
`AreaId::DungeonB1F`という単一の階層しか存在しなかった。`movement.rs`の
`try_move_player`では、B1Fの下り階段に触れると新しい階層へは移動せず、
「さらに深層への下り階段に足を踏み入れた！地下奥深くから強大な魔物の咆哮が
響く……！」という強制戦闘（`TriggerBattle`）だけが発生するプレースホルダーに
なっていた。ダイアログ（`dialogue.rs`）や案内看板（`interact.rs`）は
「南東の地下迷宮」を単数の危険地帯として語っており、フロアが1枚しかないことと
矛盾はしないが、README.mdの「次にやりそうなこと」にも「深層フロア展開」が
既に挙げられており、B1Fの下り階段のメッセージ自体が「まだ実装されていない
深層の存在」を示唆していた。

## Circumstances

「5階層ほど増やす」という要求に対し、既存のB1F単体をどう拡張するかで
以下の選択肢を検討した：

1. **`AreaId`に階層ぶんの列挙子を追加する**（`DungeonB2F`〜`DungeonB6F`）:
   既存の`AreaId::Town` / `AreaId::Village`と同じ「区域ごとに列挙子を持つ」
   というこのコードベースの一貫した流儀に従う。コンパイラの網羅性チェックが
   そのまま効く。
2. **`AreaId::Dungeon(u8)`のように深さを値として持たせる**: 将来的な階層数の
   変更に強いが、`movement.rs`・`mod.rs`のあらゆる`match`が「タプルの中身」を
   意識した書き方に変わり、既存の書き方（`AreaId::Town`のような単純な列挙子
   パターン）から乖離する。今回は「6階層で当面固定」という要求規模であり、
   将来さらに動的な階層数が必要になった時点で移行すれば十分と判断した。

1を採用しつつ、`movement.rs`側の階段処理が「1つ隣の階層へ」という単純な
加減算で済むように、`AreaId`に`dungeon_depth() -> Option<u8>`と
`from_dungeon_depth(u8) -> Option<AreaId>`のヘルパーを持たせることにした。
これにより`match`自体は列挙子を全部並べる形（網羅性チェックを保つ）を
保ちつつ、各アームの中身は「深さ+1」「深さ-1」という共通ロジックの呼び出し
だけで済み、B1F〜B6F間の5組の遷移を1つずつ手書きせずに済む。

各階層のマップ生成自体はADR-0017のCave生成（`dungeon_gen::generate`）を
そのまま使い回す。ADR-0017の「フロアは永続化しない（switch_areaのたびに
再生成する）」という方針により、階層を上り下りしても元いた階層の状態を
復元する必要がなく、全階層が同じ生成関数・同じ固定進入座標`(3, 4)`を
共有できる。

## Rationale

1. **`AreaId`列挙子を素直に追加する**: このコードベースは`AreaId`を
   `match`で網羅的に処理する書き方を徹底しており（`movement.rs`の
   `StairsUp` / `StairsDown` / `RoadExit`処理）、動的な深さ表現に変えると
   その恩恵（コンパイル時に区域追加漏れを検出できる）を失う。6階層という
   確定した規模なら列挙子を6つ並べる方が既存流儀と整合する。
2. **階層遷移ロジックだけを`dungeon_depth`/`from_dungeon_depth`で共通化する**:
   `match`の網羅性は保ちながらも、「B1F↔B2F」「B2F↔B3F」...という5組の
   ほぼ同一の遷移コードを手で複製すると変更漏れの温床になる。深さの
   加減算に落とし込めば、遷移ロジックは1箇所（`StairsDown`と`StairsUp`の
   ダンジョン共通アームがそれぞれ1つ）で済む。
3. **最深階（B6F）の下り階段は既存の強制戦闘のままにする**: B6Fより深い
   階層は今回のスコープ外。「これ以上は潜れない」という契約を
   `AreaId::from_dungeon_depth(depth + 1)`が`None`を返すことで表現し、
   `None`の場合だけ元のプレースホルダー（強制戦闘）にフォールバックする。
   これにより「未実装の深層をほのめかす」という既存のフレーバーテキストの
   演出を、実際に階層が増えた後も自然に引き継げる。
4. **進入座標`(3, 4)`と生成関数を全階層で共有する**: ADR-0017の契約
   （王都からB1Fへの進入座標は生成結果によらず必ず床）を、階層間の
   上り下り全てに拡張する。フロアを永続化しない設計上、上り階段で
   1つ浅い階層へ戻っても、その階層は移動のたびに再生成される。したがって
   「以前その階層にいた時の下り階段の位置」に戻ることはそもそも不可能で
   あり、全階層で共通の固定安全地点`(3, 4)`に着地させるのが唯一の自然な
   契約になる。
5. **難易度の階層差は今回のスコープ外**: 深い階層ほど魔物や宝箱を増やす、
   といった深度に応じた生成パラメータの調整は行わない。要求は「階層を
   増やす」ことであり、生成アルゴリズム自体（`dungeon_gen.rs`のCave生成・
   ADR-0018のテンプレート部屋）は変更していない。将来的に深度依存の
   難易度調整をする場合は、`dungeon_gen::generate`に深さを渡す形で
   別途ADRを起こす。

## Decision

`core::town::map::AreaId`に`DungeonB2F`〜`DungeonB6F`を追加し、
`AreaId::dungeon_depth(&self) -> Option<u8>`（B1F=1〜B6F=6、それ以外は
`None`）と`AreaId::from_dungeon_depth(u8) -> Option<AreaId>`を新設する。
`TownMap::create_dungeon_b1f`は`TownMap::create_dungeon_floor`に改名し、
全ダンジョン階層から共通で呼び出す（生成アルゴリズム・進入座標`(3, 4)`は
変更なし）。

`movement.rs`の`try_move_player`は、`StairsDown`のダンジョン内アームを
「現在の深さ+1の階層へ`ChangeArea`、存在しなければ（B6F）従来通り
強制戦闘」に、`StairsUp`のダンジョン内アームを「現在の深さ-1の階層へ
`ChangeArea`」に変更する。両方とも移動先の`spawn_pos`は`(3, 4)`で統一する。
B1Fの上り階段（王都へ帰還）とB1F未満（存在しない0階層）の扱いは変更しない。
