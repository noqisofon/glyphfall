# ADR-0017: セルオートマトン法による洞窟型ダンジョンのプロシージャル生成

- Status: Accepted
- Date: 2026-09-15

## Background

ADR-0010（統一見下ろし視点探索システム）の時点で、「ダンジョン構造は将来的な
プロシージャル生成への拡張を前提としつつ、第一歩としてB1Fフロアを実装する」と
明記しており、B1F自体は最初から暫定の固定マップという位置づけだった。

その固定マップ（`create_dungeon_b1f`）は、西の入口ホールから中央大通路を通って
「宝物庫」「水没した礼拝堂」「牢獄区画」「魔物の巣窟」という4つの物語的ゾーンへ
分岐する、手作りのレイアウトになっていた。ドラクエ×Daggerfallハイブリッド
（ADR-0001）という方向性上、街や重要施設は作家性の強い固定マップのままで良いが、
「潜るたびに姿を変える地下迷宮」はDaggerfall的な過剰シミュレーションの象徴であり、
本作にとって欠かせないピースである。

## Circumstances

プロシージャルダンジョン生成のアルゴリズムには、大きく分けて以下のような系統が
存在する：

1. **部屋＋通路型（BSP分割／ランダム矩形配置＋廊下接続）**: Rogue系の伝統的手法。
   人工的な「建造物」感が強く、宝物庫・牢獄のような区画分けとの相性が良い。
2. **セルオートマトン法（本ADRで採用）**: ランダムに壁／床を初期充填し、周囲8マスの
   壁数に応じて床/壁を反転させる平滑化を数回繰り返すことで、自然な洞窟状の
   不定形空間が生まれる。
3. **ドロネー三角形分割やウェーブ関数崩壊など、より高度な手法**: 実装コストが高く、
   今回のスコープには過剰。

今回は「今は洞窟っぽいやつ1種類でいい」という要求だったため、まず2を実装する
ことにした。ただし将来1のような別系統を追加する可能性は高いため、アルゴリズムを
選べる構造にしておく必要があった。

既存の固定B1Fをどう扱うかも論点だった。「宝物庫」「礼拝堂」等の物語的ゾーニングを
保つために別エリアとして追加する案と、B1Fの生成ロジック自体を丸ごと洞窟生成に
置き換える案を比較した結果、B1Fそのものを置き換える方針を選んだ（ユーザー判断）。
これにより手作りの物語的ゾーニングは失われるが、入口・出口・宝箱・魔物シンボルと
いった機能タイルは生成後に配置することで、既存の`movement.rs` / `interact.rs`の
挙動（宝箱を開ける・階段で行き来する・魔物シンボルに触れて戦闘に入る等）は
一切変更せずに済む。

また、王都からB1Fへの侵入時、`movement.rs`は`spawn_pos`を`Position { x: 3, y: 4 }`
に固定している。この座標は生成結果によらず必ず到達可能な床でなければならない、
という制約が新たに生まれた。

実装中、`HashMap`の反復順序がプロセスごとに変わることに起因して、同じ乱数シードから
生成したはずのマップが実行のたびに下り階段の位置だけ異なるという再現性バグに
遭遇した（複数マスが同じ最遠距離になるタイの場合の選択が、ハッシュの反復順序に
依存していた）。

初回実装をユーザーにレビューしてもらったところ、以下の2点が指摘された：

1. テストの`reachable > 30`という緩い閾値が、生成側の下限`CAVE_MIN_FLOOR_TILES = 80`
   と整合しておらず、「80マス保証」という契約自体がテストで直接検証されていない。
2. `fallback_corridor`の階段配置座標が、入口が盤面端に近い場合に境界列(x=0)へ
   はみ出し得る（実害はほぼないが確認要）。

1点目を深掘りする過程で、テストが使う`TileType::is_walkable()`基準の到達判定と、
生成側が使う「床タイルの4方向連結」基準の到達判定が一致しないことに気づいた。
`ChestClosed`と`MonsterSymbol`は`is_walkable() == false`（Zコマンドで調べる／
ぶつかって戦闘に入るタイルで、踏み越えて通過はできない）ため、隘路に配置すると
実際にはプレイヤーが歩いて先へ進めなくなる可能性があった。これは本ADRの
Rationaleで謳った「侵入したら詰みマップだった、という事故を構造的に防ぐ」
という保証を、宝箱・魔物の配置段階で自ら破りかねない欠陥だった。

さらに、この欠陥を修正して実測したところ、`CAVE_FILL_PROB = 0.45` /
`CAVE_MIN_FLOOR_TILES = 80`という初期パラメータでは、46×13という横に
極端に細長い盤面上で「入口を含む連結領域が80マス以上」という条件を単発の
試行で満たせる確率が実測でわずか3%程度しかなく、`CAVE_MAX_ATTEMPTS = 50`回
再試行しても約2割の確率で全滅し、`fallback_corridor`（見た目も探索性もない
一本道）に静かにフォールバックしていたことが判明した。テストが`seed 0..30`
という狭い範囲でたまたま検出できていなかっただけで、実際には無視できない
頻度で「洞窟っぽくない一本道ダンジョン」が生成されていたことになる。
RogueBasinで一般に紹介される45%という初期充填率は正方形に近い盤面を想定した
値であり、本作のような極端な横長盤面ではそのまま使えないと判断した。

## Rationale

1. **アルゴリズムの切替可能性**: `DungeonGenKind`という列挙型を導入し、
   `generate(kind, width, height, entrance, rng)`を単一のエントリポイントにする。
   現時点では`Cave`のみだが、将来「部屋＋通路型」を追加する際も呼び出し側
   （`TownMap::create_dungeon_b1f`）はアルゴリズム名を差し替えるだけで済む。
2. **入口座標の契約を守る**: 生成後に入口マスを強制的に床化し、そこから
   4方向連結で到達できる領域だけを最終マップとして採用する（到達不能な
   孤立領域は壁に戻す）。入口を含む連結領域が既定の床マス数
   （`CAVE_MIN_FLOOR_TILES = 150`）を下回ると判定し、シードを消費しながら
   生成をやり直す。これにより「侵入したら詰みマップだった」という事故を
   構造的に防ぐ。
   閾値は45%充填では実測到達率3%だったため、初期充填率`CAVE_FILL_PROB`を
   62%へ引き上げた（実測で単発到達率89%、`CAVE_MIN_FLOOR_TILES = 150`
   到達率も82%まで改善）。50回の再試行を組み合わせれば全滅確率は
   実質ゼロになる水準である。正方形に近い盤面向けの45%という一般的な値を
   そのまま使わず、実際の盤面形状（46×13の横長）に対して実測でパラメータを
   検証したことが今回の教訓である。
3. **装飾配置による到達不能化を防ぐ**: 宝箱・魔物シンボルは歩行不可タイルの
   ため、連結領域に含まれていても置き方によっては他のマスへの経路を塞ぐ
   ことがある。1個配置するたびに「入口から`is_walkable`基準で歩いて
   到達できるマスの総数」を配置前後で比較し、置いたタイル自身の1マス分を
   超えて減っていれば（＝他のマスを巻き添えにしていれば）配置を取り消す。
   これにより、連結領域内のどのマスも装飾配置によって到達不能になることは
   ない。テスト側でも、この歩行到達性を直接の基準として下り階段への
   到達可能性を検証するようにした（床マスの連結性という生成側の基準と、
   実際にゲームが使う歩行可能性という基準の食い違いを、テストでも生成器と
   同じ基準で検証する）。
4. **既存タイル語彙の再利用**: 新しいタイル種別は追加せず、既存の
   `DungeonFloor` / `DungeonWall` / `StairsUp` / `StairsDown` /
   `ChestClosed` / `MonsterSymbol`のみを生成結果に配置する。`interact.rs`の
   宝箱開封・`movement.rs`の魔物シンボル接触判定はタイル種別だけを見て
   動くため、生成器側の変更は一切不要だった。
   一方、`IronGateClosed`（鉄格子扉）と`Water`（水没床）は「牢獄」「礼拝堂」
   という物語的ゾーンに紐づく装飾だったため、自然な洞窟には持ち込まず、
   今回の生成結果からは省いた（タイル種別自体は将来の別生成アルゴリズムや
   固定マップのために残す）。
5. **RNGの受け渡し方針**: `battle::build_turn_resolution`や
   `event::try_trigger_sudden_event`など、既存コードは`<R: Rng>`をジェネリック
   引数として受け取り、具体的な`rand::thread_rng()`の生成は呼び出し側
   （`app`クレートのBevy入力ハンドラ）に委ねる方針を採っている。ダンジョン
   生成もこの慣習を踏襲し、`TownState::move_player` / `switch_area`に
   `rng: &mut R`を追加し、`core`側はシードの取り方に関与しない。これにより
   `core`は決定的な乱数（`StdRng::seed_from_u64`）で洞窟生成のテストが書ける。
6. **再現性バグの修正方針**: 最遠点（下り階段の位置）を選ぶBFS距離計算を
   `HashMap`から、座標を添字とする`Vec`（走査順は`flood_fill`が返す領域順＝
   行優先の決定的な順序）に置き換えた。乱数シードだけに生成結果が依存する
   よう、内部実装から非決定的なイテレーション順序を排除した。
7. **フロアの永続化はしない**: 街との行き来のたびにB1Fを再生成する
   （`switch_area`が呼ばれるたびに新しい洞窟が作られる）。ローグライク的な
   「潜るたびに違う地下迷宮」という体験を優先し、フロア状態の保存・復元は
   今回のスコープ外とする。

## Decision

`core::town::dungeon_gen`モジュールを新設し、`DungeonGenKind`列挙型
（現状は`Cave`のみ）と、セルオートマトン法（62%初期充填→平滑化4回→
入口を含む連結領域が150マス未満なら再試行→最遠点に下り階段配置→残りの
床マスへ宝箱2個・魔物シンボル1個を、歩行到達性を壊さない範囲でランダムに
配置）による生成関数`generate`を実装する。生成に失敗し続けた場合の保険と
して、入口から一直線に掘るだけの`fallback_corridor`を用意する。

`TownMap::create_dungeon_b1f`はこの生成器を、王都側の固定侵入座標
`(3, 4)`を入口として呼び出す形に置き換える。`TownState::move_player` /
`switch_area`はジェネリックな`rng: &mut R`引数を追加で受け取り、
`app`側のBevy入力ハンドラ（`app/src/town/input.rs`）が`rand::thread_rng()`を
生成して渡す。既存の固定マップが持っていた「宝物庫」「水没した礼拝堂」
「牢獄区画」「魔物の巣窟」という物語的ゾーニングと、`IronGateClosed` /
`Water`タイルの使用は今回のB1Fからは失われる。
